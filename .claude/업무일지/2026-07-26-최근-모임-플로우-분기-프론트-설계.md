# 최근 모임 플로우 분기 - 프론트 설계

- 날짜: 2026-07-26
- 상태: 설계 완료, 구현 예정
- 대상 레포: `dnd-14th-8-frontend`
- 연관 레포: `dnd-14th-8-backend` (같은 날짜 `최근-모임-플로우-분기-백엔드-설계.md`)
- 결정안: 최근 모임 클릭 시 사용 가능한 플로우가 하나면 즉시 이동하고, 일정/중간지점이 모두 가능하면 선택 UI를 제공한다.

## 배경

랜딩 홈의 최근 모임은 사용자가 같은 브라우저에서 생성했거나 참여한 모임으로 다시 들어가는 진입점이다. 현재 프론트는 최근 모임 카드를 클릭하면 항상 `/meetings/{meetingId}/schedule`로 이동한다.

하지만 실제 모임은 다음 세 가지 상태가 가능하다.

| 상태 | 기대 동작 |
|---|---|
| 일정 조율만 사용 | 일정 조율 화면으로 이동 |
| 중간지점 찾기만 사용 | 중간지점 화면으로 이동 |
| 일정 조율과 중간지점 모두 사용 | 사용자가 진입할 화면을 선택 |

따라서 최근 모임 목록 응답에 모임별 사용 가능 플로우 정보가 필요하고, 프론트는 그 값을 기준으로 라우팅해야 한다.

## 현재 상태

| 항목 | 상태 |
|---|---|
| 최근 모임 API | `GET /api/meetings/me?localStorageKey=...` |
| 프론트 응답 타입 | `MyMeetingResponse`에 플로우 정보 없음 |
| 최근 모임 클릭 | 항상 `/meetings/{meetingId}/schedule` |
| 위치 메인 경로 | `/meetings/{meetingId}/location/stations` |
| 일정 메인 경로 | `/meetings/{meetingId}/schedule` |

현재 고정 라우팅은 장소 모임만 만든 사용자를 일정 화면으로 보내는 문제가 있다.

## 백엔드 계약 필요 사항

최근 모임 응답에 다음 필드가 추가되어야 한다.

```ts
type MeetingFlow = "SCHEDULE" | "LOCATION";

interface MyMeetingResponse {
  meetingId: string;
  hostName: string;
  participantCount: number;
  createdAt: string;
  isHost: boolean;
  availableFlows: MeetingFlow[];
}
```

`availableFlows`는 화면 진입 가능한 플로우 목록이다.

- `["SCHEDULE"]`: 일정 조율만 진입
- `["LOCATION"]`: 중간지점 찾기만 진입
- `["SCHEDULE", "LOCATION"]`: 선택 UI 표시

## 사용자 흐름

```mermaid
flowchart TD
    A[랜딩 최근 모임 카드 클릭] --> B{availableFlows 개수}
    B -->|0개 또는 누락| C[기본값: 일정 조율로 이동]
    B -->|1개: SCHEDULE| D[/meetings/{meetingId}/schedule]
    B -->|1개: LOCATION| E[/meetings/{meetingId}/location/stations]
    B -->|2개| F[선택 UI 표시]
    F --> G[일정 조율 보기]
    F --> H[중간지점 보기]
    G --> D
    H --> E
```

누락 또는 빈 배열은 백엔드 배포 순서 차이를 고려해 기존 동작인 일정 조율 화면으로 폴백한다.

## 선택 UI 설계

최근 모임 카드 클릭 시 `availableFlows`가 2개면 모달 또는 바텀시트를 띄운다.

권장 UI:

- 제목: `어디로 이동할까요?`
- 설명: `{hostName}님의 모임에서 확인할 화면을 선택해주세요.`
- 액션 1: `일정 조율 보기`
- 액션 2: `중간지점 보기`
- 보조 액션: `취소`

랜딩은 모바일 중심 화면이므로 기존 `Modal` 컴포넌트를 우선 검토하고, 액션이 2개 이상일 때 시각적으로 어색하면 별도 바텀시트형 컴포넌트로 분리한다.

## 라우팅 정책

| availableFlows | 동작 |
|---|---|
| `["SCHEDULE"]` | `/meetings/{meetingId}/schedule`로 이동 |
| `["LOCATION"]` | `/meetings/{meetingId}/location/stations`로 이동 |
| `["SCHEDULE", "LOCATION"]` | 선택 UI 표시 |
| `[]`, `undefined` | 기존 동작 유지: `/meetings/{meetingId}/schedule` |

프론트는 `availableFlows` 배열 순서에 의존하지 않고 포함 여부로 판단한다.

## 테스트 계획

### 자동 테스트

- 일정 플로우만 있는 최근 모임 클릭 시 일정 화면으로 이동한다.
- 중간지점 플로우만 있는 최근 모임 클릭 시 중간지점 화면으로 이동한다.
- 두 플로우가 모두 있는 최근 모임 클릭 시 선택 UI가 렌더링된다.
- 선택 UI에서 일정 조율 보기를 누르면 일정 화면으로 이동한다.
- 선택 UI에서 중간지점 보기를 누르면 중간지점 화면으로 이동한다.
- `availableFlows`가 없거나 빈 배열이면 기존 일정 화면 이동으로 폴백한다.

### 수동 검증

1. 일정 조율만 진행한 모임을 최근 모임에서 클릭한다.
2. 중간지점 찾기만 진행한 모임을 최근 모임에서 클릭한다.
3. 일정 조율 후 중간지점까지 진행한 모임을 최근 모임에서 클릭한다.
4. 세 번째 케이스에서 선택 UI가 뜨고 두 경로가 모두 정상 동작하는지 확인한다.

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 백엔드 배포 전 `availableFlows`가 없음 | 일정 화면으로 폴백해 기존 기능 유지 |
| 백엔드가 poll 존재 여부로 계산하면 항상 둘 다로 오판 | 백엔드 문서에서 생성 플로우와 실제 사용 데이터 기준을 명시 |
| 선택 UI가 홈 첫 화면에서 과하게 느껴짐 | 단일 플로우는 즉시 이동하고 복수 플로우에서만 표시 |
| 기존 테스트가 SSR 중심이라 클릭 검증이 부족 | 필요한 경우 React Testing Library 기반 인터랙션 테스트를 추가 |
