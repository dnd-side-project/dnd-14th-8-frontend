# 모여락 화면 문구 쓰기

규칙은 `ux-writing/rules.json`에 있다. 이 문서는 규칙을 옮겨 적지 않고, 규칙 파일을 읽고 쓰는 순서만 적는다. 규칙과 이 문서가 다르면 규칙 파일이 맞다.

## 쓰는 말

- 규칙 파일: `ux-writing/rules.json`. 용어(`terms`), 규칙(`rules`), 예외(`exceptions`), 검사 범위(`scope`)가 들어 있다.
- 자동 검사: `src/ux-writing.test.ts`. 코드에서 문구와 그 위치를 읽어 규칙 파일과 대조한다. `pnpm test:ux-writing`으로 실행한다.
- 예전 위반 목록: `ux-writing/baseline.json`. 자동 검사를 처음 넣을 때 이미 규칙을 어기고 있던 문구다.
- 위치: 문구가 화면의 어디에 나오는지를 가리킨다. 규칙 파일의 `legend.where`에 종류가 있다(성공 토스트, 모달의 확정 버튼, 화면 아래의 큰 버튼 등).
- 후보 검사: `pnpm ux-writing:try --where <위치> "후보 1" "후보 2"`. 코드에 넣기 전의 문구를 규칙에 대 보고, 토스트면 너비도 보여 준다.

## 순서

1. `ux-writing/rules.json`을 처음부터 끝까지 읽는다. 문구를 쓰기 전에 읽는다.
2. 쓸 문구의 위치를 정한다. 토스트인지, 모달 버튼인지, 화면 아래의 큰 버튼인지에 따라 지킬 규칙이 달라진다. 위치별 규칙은 `group`이 "위치별"인 규칙이다.
3. 같은 화면과 앞뒤 화면의 문구를 코드에서 찾아 읽는다. 사용자가 방금 누른 버튼의 이름과 지금 보고 있는 화면의 제목을 확인한다. 실패 문구의 동사는 그 버튼의 말을 쓴다.
4. 문구를 쓴다. `use`에 적힌 말을 쓰고 `avoid`에 적힌 말은 쓰지 않는다. `terms`의 용어는 뜻이 맞는 곳에만 쓴다. 규칙의 고칠 말(`fixes`)로 정해지지 않는 문구는 아래 "대안을 2개 이상 내고 사람이 고른다"를 따른다.
5. 자동 검사가 확인하지 못하는 규칙을 직접 확인한다. `auto`가 "none"인 규칙은 모두 직접 확인하고, "partial"인 규칙은 정해 둔 표현 말고도 같은 문제가 없는지 본다.
6. `pnpm test:ux-writing`을 실행한다. 실패하면 문구를 고친다.
7. 문구를 넣은 화면을 실제로 띄워서 확인한다. 줄이 넘치지 않는지, 앞뒤 문구와 말이 맞는지 본다.

## 대안을 2개 이상 내고 사람이 고른다

문구 하나가 규칙만으로 정해지지 않으면 AI가 혼자 고르지 않는다. 새 화면의 문구를 처음 쓸 때, 긍정형(S03)처럼 뜻을 읽어야 하는 규칙에 맞춰 문장을 바꿀 때, 규칙은 지켰지만 사용자가 읽기에 뜻이 흐릴 수 있을 때가 여기에 해당한다. 규칙의 고칠 말(`fixes`)로 바꾸는 경우는 하나로 정해지므로 대안을 내지 않는다.

1. 대안을 2개 이상 만든다. 서로 다른 방향이어야 한다(예: 이유를 말하는 문장과 할 수 있는 것을 말하는 문장, 숫자를 넣은 문장과 넣지 않은 문장). 글자만 조금 다른 대안은 하나로 친다.
2. 대안을 모두 `pnpm ux-writing:try`로 돌린다. 자동 검사에 걸리는 대안은 고치거나 빼고, 왜 뺐는지 적는다.
3. 대안마다 아래를 표로 적는다.
   - 문구
   - 사용자가 읽는 뜻: 이 문구만 보고 무엇을 알게 되는가
   - 지킨 규칙과 걸리는 규칙, 자동 검사가 보지 못하는 규칙을 직접 확인한 결과
   - 토스트면 너비(변수가 있으면 가장 긴 값을 넣어 잰다)
   - 같은 화면의 다른 문구와 맞는지(같은 말을 되풀이하는지, 다른 말로 부르는지)
   - 코드를 바꿔야 하는지(예: 숫자를 넣으려면 변수가 필요하다)
4. 추천 하나를 표시하되, 사람이 고르기 전에는 확정하지 않는다. 대화 중이면 표를 보여 주고 묻는다. PR로 넘길 때는 추천을 넣고, PR 본문의 "문구 대안" 표에 나머지 대안과 함께 적어 확인을 받는다.
5. 사람이 고른 문구가 다른 화면에도 쓸 원칙을 담고 있으면(예: "토스트에는 숫자를 넣는다"), 규칙으로 만들지 사람에게 묻는다.

## 자동 검사가 실패했을 때

- "예전 위반 목록에 없는 위반이 없다"가 실패하면 새로 쓴 문구가 규칙을 어긴 것이다. 문구를 고친다. 예전 위반 목록에 더해서 통과시키지 않는다.
- "고친 위반은 예전 위반 목록에서 지운다"가 실패하면 예전 위반을 고친 것이다. `UX_WRITING_UPDATE_BASELINE=1 pnpm test:ux-writing`으로 목록을 다시 만든다. 이 명령은 항목의 개수를 남은 위반 수로 줄이고, 남은 위반이 없는 항목은 지운다. 목록에 새 항목이 생기거나 개수가 늘면 파일을 쓰지 않고 실패한다.
- 사람이 규칙을 새로 정해 기존 문구에서 위반이 나오면, 그 규칙 번호를 적어 목록에 더한다(`UX_WRITING_UPDATE_BASELINE=1 UX_WRITING_BASELINE_ALLOW_RULES=W22 pnpm test:ux-writing`). 규칙을 새로 정하지 않았는데 이 방법으로 새 위반을 더하지 않는다.
- 토스트 너비(P02)가 실패하면 문구를 줄인다. 너비는 글꼴 파일의 글자 폭으로 계산한 값이고, iOS Safari와 Android Chrome에서도 넘지 않도록 자간을 뺀 값으로 본다.
- 규칙이 틀렸다고 생각하면 문구를 규칙에 맞추지도, 규칙을 고치지도 말고 사람에게 묻는다.

## 예외를 따지는 순서

1. 규칙을 그대로 지킬 수 있는지 먼저 본다.
2. 지킬 수 없으면 `exceptions`에 같은 경우가 있는지 찾는다. 있으면 그 예외를 따르고, 어느 예외인지 PR에 적는다.
3. 같은 경우가 없으면 예외를 새로 만들지 않는다. 문구 후보와 이유를 적어 사람에게 묻는다.

## 사람이 정하는 것

- 규칙을 새로 만들거나 바꾸는 일
- 예외를 더하는 일
- 화면에 처음 나오는 용어의 이름
- 규칙만으로 정해지지 않는 문구(위 "대안을 2개 이상 내고 사람이 고른다")

정한 내용은 `ux-writing/rules.json`에만 적는다. 규칙마다 이유(`why`)와 근거(`source`)를 함께 적고, 자동 검사가 확인할 수 있으면 검사(`check`)와 예시(`examples`)를 넣는다. 다른 문서에 같은 규칙을 다시 적지 않는다.

## 자동 검사가 읽지 못하는 것

- 관리자 화면(`src/domains/admin/`)은 검사하지 않는다.
- 서버가 내려 주는 문구와 디자인 시스템 컴포넌트의 기본 문구는 읽지 못한다.
- 토스트에 넘기는 문구가 다른 값에서 만들어지면(예: 입력 검증 결과의 메시지) 토스트로 읽지 못하고 그 밖의 문구로 읽는다.
- 변수 자리가 있는 토스트 문구는 너비를 계산하지 못한다. 들어갈 수 있는 가장 긴 값으로 화면에서 확인한다.
- 화면 제목이 다른 파일에 있으면 "추가하거나 수정하는 화면"인지 알지 못한다(P09).
